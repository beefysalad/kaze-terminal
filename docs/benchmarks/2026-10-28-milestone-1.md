Run with `bench/run.ps1` on Patrick's Windows laptop, kaze at `feature/plan-1-terminal-core`
plus the bench mode commit. Default config (pwsh 7 from the Store, 14pt, 1100x720dp window,
10,000 lines of history), except where a row says otherwise. "Ready prompt" means the first drawn frame with any
non-blank text; with pwsh and cmd.exe that is the prompt. Raw logs and `results.json`
are in `%USERPROFILE%\Desktop\kaze-wt\bench\` (the harness's default output folder next to the checkout, not in the repo). The macOS run is still to do (on the MacBook,
with `bench/run.sh`).

## Missed goals, and what was measured

### Keypress to glyph: 24.6ms p50, goal 10ms

What was measured: 200 synthetic keys (`x`, then Backspace, alternating, 50ms apart) injected
inside kaze through the same `route` path a real key uses, into pwsh at its prompt. Each key is
timed from being routed to the end of the first drawn frame whose cursor moved.

- 24.6ms p50, 38.3ms p99, 12.9ms min, 43.5ms max. No key was dropped.
- Most of it is the shell: the echo takes pwsh/PSReadLine plus ConPTY. In half the keys the echo
  came in two pieces with a frame drawn in between (`frames_between` p50 1, max 2).
- From the last shell output kaze had before the echo frame to that frame's end: p50 8.4ms,
  p99 24.1ms. In this run the stamp was the last change signal of any kind before the frame
  *ended*, so output that arrived after the frame copied its rows could count, which can only
  make these numbers smaller than kaze's real share. The fix after this run counts only output
  signalled before the frame event; it was not re-measured. Building and submitting a frame
  takes 0.5ms (p50), so most of this is waiting for the next frame.
- Not included at all: keyboard to window (OS input) and frame to screen (compositor). On a
  60Hz display those add roughly one more refresh, so on-screen latency is higher than 24.6ms.

What this run shows: with pwsh, routing a key to seeing its echo drawn took 12.9ms at best and
24.6ms typically, and most of that is spent before kaze has the echo. Whether 10ms is reachable
with pwsh was not tested (no other shell, no tuned PSReadLine). kaze's part might shrink by
drawing as soon as output arrives instead of on the next paced frame. A camera or hardware probe
is needed for a true glass-to-glass number.

### Launch to ready prompt: 1,266ms median, goal 500ms

What was measured: process creation (`GetProcessTimes`) to the end of the first frame with any
non-blank text, which is pwsh's prompt. Five runs with the default shell, three with cmd.exe.

| | pwsh (5 runs) | cmd.exe (3 runs) |
|---|---|---|
| First frame (empty window) | 415-485ms | 399-500ms |
| First shell output | 577-662ms | 570-665ms |
| Ready prompt | 1,223-1,614ms, median 1,266ms | 590-693ms, median 605ms |

kaze alone takes about 450ms to its first frame, already near the whole budget; with cmd.exe the
prompt is up at about 600ms, so kaze misses 500ms even with a fast shell. pwsh adds about 650ms
on top. Where the 450ms goes (window and GPU setup, fonts) was not broken down in this run.
Every run's first frame is also its slowest (about 115-385ms), counted as one late frame per run.

## How each number was measured

All timings come from kaze's bench mode (`KAZE_BENCH=1`, see `bench/README.md`). It is in-process:
it excludes OS input delivery and compositor latency. Frame time is from kaze receiving Gio's
frame event to `Frame` returning, so it covers building the frame and handing it to the GPU,
not the time until it is shown.

- **Streaming.** `bench/flood -claude` writes the Task 7 capture (`claude-7.bin`, Claude Code's
  first screen, 1.4KB) with its queries and input-mode switches removed (OSC and DCS strings are now removed too), then streams a reply
  for 10s the way Claude Code's renderer does: finished lines printed once, and a live region
  (the last lines of the paragraph, a spinner and the input box) redrawn in place every 16ms
  inside synchronized-update markers. 625 repaints, 669KB. The capture has no timestamps, so
  "original speed" could not be reproduced. A plain flood of 10,100 colored lines (ASCII,
  Japanese, 16/256/truecolor) took 183ms to write and drew 413 frames, none over 16.7ms
  (p50 3.2ms, max 8.2ms).
- **Frame counts** come from the phase named in the table: `after_type` runs from the typed
  command to exit, `scroll` from the scroll start to the top. Every frame in both was drawn
  (none held back by synchronized output). The launch frames, including each run's slow first
  frame, are outside both phases.
- **Flicker and tearing** were not measured. No frame took over 16.7ms to build and submit, but
  that does not prove no refresh was dropped later in the GPU or compositor; nothing here sees
  that. kaze honors synchronized output (the stream uses it); tearing depends on the swap chain
  and needs a visual check.
- **Scroll.** After the flood filled history to its 10,000-line cap and it stayed still for 1.5s,
  kaze injected wheel events for one page per frame until the top. Every frame rasterized the
  whole screen (10,688 rows over 334 frames).
- **Idle CPU and memory.** The harness read `TotalProcessorTime` and `PrivateMemorySize64` of the
  kaze process at 10, 40 and 70s after start, with 4 tabs open and nothing running. Bench mode
  adds no timers of its own in an idle run.
- **Per-tab cost.** 1 tab and 4 tabs, each tab filled with 10,100 flood lines (history full at
  10,000), read 25s after start: 187.3MB and 277.9MB, so (277.9 - 187.3) / 3 = 30.2MB per full
  tab. That is the history's cells at the default width. Idle: 147.4MB (1 tab) and 148.8MB
  (4 tabs), so 0.5MB per idle tab in kaze itself.

## Run notes

- kaze was started through WMI so it would not take focus from Patrick's windows. It still took
  the foreground in 4 of about 30 launches (Windows lets any process take it once there has been no
  input for a while). In the first full run, before input blocking existed, 11 real keystrokes
  reached an idle bench window (no command was run; that run was discarded). The runs above had
  real input dropped by a harness flag; after review, bench mode drops all real input by
  default (`KAZE_BENCH_ALLOW_INPUT=1` to opt out) and the harness launches with
  `SW_SHOWNOACTIVATE`. One
  4-tab idle window was closed early during the second run (likely by hand, after it took focus);
  the idle runs were repeated and the numbers above come from the clean repeat.
- The first full run also put three bench commands into Patrick's real PowerShell history (the
  Store pwsh ignores the `APPDATA` override). Runs now start pwsh with history saving off.
- macOS: `GOOS=darwin go vet` passes for every package except `internal/ui`, `cmd/kaze` and
  `spike/gio` (Gio's darwin build needs cgo). `internal/render` and `internal/input` import Gio
  too but vet cleanly with cgo off.
